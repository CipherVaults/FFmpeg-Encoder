# Windows release engineering: what to carry forward from v0.6 Beta and v0.7 Alpha

**Evidence cutoff: 21 November 2026.** Continuation guide for package qualification and Milestone S. This note records lessons, not authorization to start work or a claim that v0.7 has shipped. Keep the Windows Alpha release lane separate from regular v0.7 development. Regular development remains paused at the [safe stopping point](2026-11-21_Regular_v0.7_Safe_Stop.md).

## Beta: close the loop from package to download

1. **A successful build is not an end-to-end pass.** An early Beta installer and portable ZIP were created, but the [first real encode checks failed](https://github.com/CipherVaults/FFmpeg-Encoder/commit/9821d5e60c899e6daeb819909669b2b1d4fa5550) because the new engine did not carry all required metadata through re-encoding. Fixing package manufacture alone would not have caught it. Trace failures through the output and the application's independent verifier, not only the packager or process exit. Exercise tagged fixtures in both MP4 and Matroska. Keep the output validator strict; preserve only the finite metadata keys that belong to the command contract.
2. **Make build inputs explicit.** Pin the Electron archive and both media executables before packaging; record which packaging inputs, launcher resources, and runtime notices are present. Target installer and portable lifecycle checks separately. An installation pass does not prove the ZIP can run from a fresh directory. A portable run does not cover uninstall or preservation of user files.
3. **Test the bytes actually shipped.** A later documentation or notice change can produce a different package, even if no application logic changed. Rebind package-level checks to the manufactured candidate and record any reuse of earlier evidence as scoped reuse. Check corresponding engine source, third-party notices, release tag and branch identity, and the final asset names and hashes. After publishing, independently download as a signed-out viewer and compare the bytes with the expected lengths and SHA-256 values. Editing a release description or changing its pre-release flag does not rebuild artifacts; verify which files stayed unchanged rather than treating the edit as a new build.

## Alpha: the engine change is not a string replacement

Start by recording the exact Git revision, platform and architecture, the digest of **each** executable, and the joint identity derived from that pair. Dynamic runtime selection and the evidence harness must agree on that identity. A route sealed against a 9.0.2 pair is not qualified for a 9.1 pair merely because a binary name or semver check passes. An identity refusal before process launch is neither an encode failure nor a pass. Do not edit the expected ID just to get a run: first establish the new pair and its provenance, then qualify the affected routes and update their evidence together. Audit Remux, range, resize and FLAC separately; they share neither every admission rule nor every test. At the cited Alpha snapshot, six Remux routes and seven operation-family cells still carry evidence tied to the older Windows pair.

### Investigate warnings and long-file refusals separately

- A truthful metadata warning is not equivalent to a fatal verification refusal. Record metadata scope (container or stream, with stream index when applicable), key, old and new values, route and exact pair. Keep expected warnings narrowly bound to the identified source/engine behavior; a new encoder tag warning does not authorize ignoring other warnings or every occurrence of a vendor ID change.
- A final-packet duration mismatch does not identify the affected stream or prove that playback changed. Investigate audio and video independently. The linked native-timing change demonstrates one narrow AAC case: a full final encoded frame can be trimmed to the intended playback interval by an edit list. Before treating any new long-file mismatch as representational, compare the actual stream and sample index, native sample table, bound edit interval, and edit-aware decoded audio; verify the video separately. Keep a negative fixture with real added or lost audio. Do not widen the general packet tolerance or assume that a different tail has the same cause. This procedure is not a passing long-file receipt.
- A run ceiling can prevent a case from starting. Record per-case terminal state: passed, expected refusal, unexpected refusal, failed, canceled, skipped, or not run. Split expensive routes into separately bounded batches with unique receipts. Before diagnosing media failures, establish that the correct tools actually ran, with the intended arguments, and that the harness captured their exit statuses.

### Future AAC tail check: three independent witnesses

1. **Coded stream:** Use the same pinned FFprobe executable from the verified pair to compare the ordered AAC packet payload hashes and codec configuration for the two artifacts. Save the exact final packet and its stream/sample index. [FFprobe data hashes](https://ffmpeg.org/ffprobe.html).
2. **Container timing:** Independently read the AAC track's native sample durations and edit-list entries, including both time scales. Compute the presented interval with exact rational arithmetic. Do not round it to milliseconds and then compare. An edit-disabled decode can help locate padding, but it does not describe how any particular player behaves. [FFmpeg MOV/MP4 edit-list handling](https://ffmpeg.org/ffmpeg-formats.html#mov_002fmp4_002f3gp).
3. **Presented audio:** With the same pinned decoder and explicit edit handling on both inputs, preserve decoder precision and original sample rate and channel layout. Compare continuous PCM hashes and per-channel sample counts; verify timestamps separately. FFmpeg's default [framehash](https://ffmpeg.org/ffmpeg-formats.html#framehash) converts audio to 16-bit PCM and therefore cannot prove equality at a higher precision by itself. Include a genuinely changed sample or timeline that must still be refused. Save input/output file hashes and outcome for each witness, including anything not run.

## Milestone S: acceptance record, not a running test total

Record one identity chain: **source commit and tree → runtime binary hashes and configuration → exact package SHA-256 → exact tested artifact → signed-out download**. Save distinct evidence for:

- **Source:** selected CI jobs on the exact checkout, expected refusals, and meaningful negatives. If CI is on a curated export, distinguish missing Git history, missing packager/runtime inputs, parked checks and true product failures. Do not add overlapping suite totals or treat historical logs as a final receipt. Exercise line-ending-sensitive tests on both platforms; normalize fixture *markers* only where line endings are irrelevant, never the bytes a test is meant to authenticate.
- **Packaged application:** installer and portable ZIP tested separately. Exercise fresh start, a representative encode/decode and verified remux, cancellation and process cleanup, restart/settings persistence, and installer uninstall. Use approved fixtures and record platform, exact binary identities, expected warnings and results. Hosted Windows, Windows Sandbox, native Windows, and a physical GPU are distinct evidence. Check AMD, Intel and NVIDIA claims separately; untested hardware stays unverified.
- **Distribution:** match the corresponding source and notices to what is actually bundled, including external codec libraries and relevant toolchain configuration. A source archive for another build or matching upstream tarballs do not complete correspondence for the current binary. Validate the source archive opens and record source, installer, portable and checksum assets independently.
- **Linux:** reuse the receipt structure, never the Windows binaries, driver evidence, or engine-result rows. A Linux engine rebuild and package need their own confirmed inputs, a controlled build environment, field checks, and corresponding source.

Stop if identity is ambiguous, the evidence is for a different artifact, or a route exposes a new warning/refusal without a justified expectation. Report what passed and what remains open. Do not publish or restart regular development based on this note.
