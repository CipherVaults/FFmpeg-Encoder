## How to run the work in parallel

The lead chooses one user-visible behavior per slice and names the requirement, one ordinary case that must succeed, a meaningful refusal or failure case and the smallest evidence needed. Independent authors can work in isolated trees against a named base. One integrator owns the shared checkout; one heavy media/desktop campaign owns the relevant resources at a time. Compatible work proceeds in parallel, not concurrent writes to the same source or the same evidence.

| Lane | Do now | Proof owed |
| --- | --- | --- |
| **Shared product** | Reuse the operation contracts, encoder service and renderer. Put portable choices, source/output invariants, timing math and user-facing state here. Keep platform mechanisms out of the contract. | Exercise the same input and expected verdict on both hosted OSes where feasible. Add a focused regression on the affected seam, including a valid input that must not be refused. |
| **Linux** | Compose the shared behavior with the pinned executable pair, owned child lifecycle, filesystem guards and native UI. Continue genuine 1440p/4K, long-file, cadence/orientation and audio work under the existing E3/E4 gates. | Real service output with independent media checks; relevant native journey, source identity, safe cancellation and closed children. | **Windows before the PC** | Prepare the same contract suites, Windows adapter tests and target build/preflight inventory; reconcile outstanding PC-only changes on paper. Test them on hosted Windows when available. Keep paths, reparse/locking behavior, runtime discovery, output opening and packaging explicit. | Record actual hosted checks and gaps; do not label a simulated dialog, cross-build or injected device native desktop or RTX evidence. No changes to the owner’s existing checkout are implied. |

**Immediate sequence.** Do not rerun the audited 054 journey or reintegrate the three CI files. Complete 055 documentation and ordered preservation; then inspect the first hosted Ubuntu and Windows jobs for the specific event revision, including skips or unavailable runners. Meanwhile prepare the next user-visible E3 case using the 1440 proposal and the requirement ledger, not another selector-only demonstration. Rebind and review that proposal on the selected base before the next authorized actual-service campaign; qualify its output, cancellation and source protection before widening the advertised range. In parallel a worker may prepare the Windows handoff and source-only checks. If a job is blocked by runner availability, permissions, corpus or hardware, note exactly which claim waits and keep unrelated lanes moving. The additive document may be preserved separately; it need not hold up CI or qualification.

After this slice, use the existing plan for the backlog: reconcile remaining remux/corpus work separately from high-resolution trim/resize; qualify audio, subtitles and vendor-specific checks against their own contracts. Continue with integrated workbench journeys and final-source QA before packaging. Working on an independent item while a PC-only proof waits does not close or remove the blocked requirement.

**Test what the current product promises.** CI starts deliberately small: read-only repository access, immutable action pins, no stored checkout credentials, no media payloads or publication. Extend it when a real regression warrants the cost: a reproducible CPU service fixture first, then a bounded Electron smoke, then target staging at the appropriate packaging gate. Save the raw child exit before interpreting a runner’s output; record commands, revision, platform and skipped/unrun cases. The 054 reporter mismatch is why an apparent pass in a log is not a missing exit receipt. Investigate a historical red: reproduce a current defect or map it to a retired contract/missing fixture with a reason. Preserve the old failure; do not rebuild obsolete behavior, weaken current assertions, or silently exclude an applicable test to make a dashboard green.

Treat renderer and media input as untrusted. Keep file selection, bounded process arguments and publication authority in main/service; test no overwrite, stale grants, collision, process timeout/cancel/drain and sanitized diagnostics where affected. Inspect both false acceptance (wrong output allowed) and false refusal (ordinary valid file rejected). Check actual output, not just FFmpeg exit or a capability flag. Review proportionate to risk; use a fresh reviewer for authority, publication and recovery changes. A focused defensive review is not a whole-repository security certification.
