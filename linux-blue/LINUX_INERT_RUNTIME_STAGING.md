# Linux runtime descriptor and inert staging contract

This additive source-only slice is not connected to main.js, the workbench, IPC, package scripts, a production catalog or any default. Existing Windows verifier/build code is unchanged. It creates no executable runtime handle, launches no process and performs no downloads or installation.

## Implemented boundary

`src/linux-runtime-descriptor.cjs` describes only the already inspected Linux x64 candidate pair with relative `runtime/ffmpeg` and `runtime/ffprobe` paths and exact existing byte/digest identities. It records the observed GLIBC_2.38 requirement, unresolved dependencies and release blockers. These observations do not define a supported distro/CPU/desktop matrix. No executable/library bytes or raw report are added to source.

`verifyLinuxStagingPair({root})` checks only that fixed pair. It rejects unknown/getter options, wrong platform/architecture, noncanonical or linked roots/ancestors, links/multiple-link files, missing, resized or tampered files, and observed file identity changes across bounded descriptor reads. It returns an inventory with `usableForEncoding:false`, no executable paths or production capability. No caller manifest, PATH lookup or renderer-controlled identity is accepted. The JSON descriptor emitted in a staging tree is an informational copy; the verifier's authority remains its fixed code descriptor, not that file.

`stageLinuxInertTree({sourceRoot,runtimeRoot,outputParent})` reuses the existing Windows app-source allowlist and candidate package-version selection, without invoking the Windows builder. It verifies the fixed pair; reserves a new exclusive sibling output; copies only allowed app source/assets and pair bytes; writes an explicit not-for-distribution notice and relative hash inventory; and rereads sources, pair and staged bytes before returning. It preserves the app icon license/provenance files already selected by the shared allowlist. It does NOT substitute those notices for missing runtime licenses: `runtimeNotices: not-staged-unreviewed` and release blockers remain explicit. No ASAR, Electron packaging, archives, executable permission bits or activation are produced. Source/candidate bytes may exist in the inert directory, but this is not a runnable app.

Bounds: at most 1,024 source files, 32 MiB per source, 64 MiB total source, fixed exact pair sizes, and a measured 27 GiB residual plus admitted staging allocation. Each file is exclusively created with non-executable mode and read back. Existing output directories/partial failures are never overwritten or cleaned automatically. All manifest inventory paths are relative; independent staging at two locations yields the same identities and relocated pair verification.

## Tests and honest limits

Ten file/injected controls pass with inert, non-executable byte fixtures. Tests replace the descriptor only inside a VM-loaded test module; no production argument enables alternate pins. Capacity observations in fixture tests are injected, including low-space refusal, because the temporary filesystem has a different capacity from the project workspace. No real candidate payload was staged or executed.

Existing Windows candidate-runtime and packaging regression run: 33 pass, one failure because this fresh source-only sibling has no installed `@electron/packager`. The failing test needs actual ASAR tooling; no package was installed and the test was not silently skipped. Syntax checks pass. A later environment with existing approved dependencies must rerun that ASAR control; there is no claim of a complete packaging pass.

Residual risks: same-user malicious filesystem swaps between checks and filesystem dispatch are not eliminated; free-space checks are point observations, not quotas; memory includes up to the bounded source set and one fixed pair file. Source allowlisting follows the existing Windows rule that includes `.cjs` modules from `src`; it does not recursively ingest arbitrary directories. Adding a file here creates no production catalog permission. The dependency closure, corresponding source/runtime notices, older glibc baseline, Linux Electron identity and native execution remain unresolved.

## Recommended integration and next product slice

After independent source review, integrate these four new paths only, rerun affected source/Windows tests with approved dependencies, and preserve the coherent checkpoint. Keep the feature unconnected until a separate reviewed Linux production composition/catalog plan exists. The next useful implementation is a selected dependency/notices bundle and exact Linux Electron resource staging on an explicitly chosen baseline, followed by bounded native package verification. Do not bundle this machine's libc/loader or repurpose developer calibration reports as product authority merely to make a package launch. No default target, distro/GPU support, public redistribution or release readiness is implied.

## Concrete next product wiring checkpoint, not another inert layer

The next checkpoint should deliver an **explicitly launched Linux product candidate using the existing app shell**, with one genuinely enabled, reviewed CPU family and unsupported modes honestly disabled. It should open without any `linux-blue/artifacts` report and store state under application user data. That is the vertical product slice; additional inert helper modules are not the goal.

Small implementation outline:
1. Separate only the runtime/service composition in `main.js` behind a main-owned platform composition factory. Preserve the existing Windows branch and `FAMILIES`/`POLICY_ID` verbatim. An explicit Linux candidate entry supplies its own verified pair/dependency identity and accepted Linux policy set; reuse existing IPC, preload, renderer, shutdown and OutputAccess. Do not treat all Windows native backend/HDR/Remux policies as Linux-compatible merely because shared EncoderService can be constructed.
2. Implement the Linux branch against the existing shared service/selector/collector/validator primitives, not by importing the entire developer workbench. Begin with one completed CPU route whose native proof has been accepted, for example the 1440p30 → 720p precision-FLAC range after its pending native journey passes. Its exact H265/slow/CRF25 and source-shape/resource restrictions remain. Other modes return unavailable. Do not enable a family before its actual proof is accepted, or borrow an unrelated Windows/GPU cell.
3. Replace the *product dependency* on a raw report with one narrowly reviewed, bundled Linux qualification record. That record must name the accepted runtime and dependency identities, exact family/settings/source bounds, validator/resource policy versions, supporting original report/audit/native proof hashes, and the explicit integration decision approving that scope. Review the conversion against originals before shipping it. Merely hashing a raw report, resealing a catalog or copying a developer capsule is not that approval. Keep originals in durable engineering records; production loads only the exact bundled accepted record through a fail-closed parser. Changed runtime or producer semantics require scoped requalification, not refreshed hashes to satisfy a test.
4. Finish a real Linux runtime verifier, distinct from the current inventory-only utility: verify the selected pair and dependency closure before it can create a genuine operation-runtime handle. Resource paths are package-relative; no renderer/environment selection. For the first internal candidate, explicitly target the existing inspected Linux x64 environment and require its exact known dependency identities. This is a constrained internal launch target, not broad distro support. Wider distribution requires a selected baseline/rebuild or reviewed private-library layout; never package the current libc/loader or add a general LD_LIBRARY_PATH shortcut.
5. Stage the actual Linux Electron shell and this composition under a fresh directory, using exact pinned Linux Electron bytes/notices and the existing source allowlist/ASAR verification approach. Launch from a second location after removing access to original workspace report paths. Perform one real UI-selected publication, output-access check and shutdown/drain, then independently audit it. This is the acceptance event for the vertical slice, not simply another inventory test.

Minimum inputs before wiring an encoding-capable Linux entry: accepted native proof for the chosen first family; a reviewed compact policy/integration decision tied to those originals; exact runtime/dependency strategy and intended internal target; approved Linux Electron identity; and license/source inventory for whatever is actually bundled. These are engineering evidence/selection tasks, not a reason to ask the owner to design the architecture. Public package format, wider distro/architecture support, GPU qualification and distribution approval can remain explicitly pending without blocking this internal product slice. If the 1440 native proof is still pending, implement its disabled composition and pure tests in parallel, then enable only after acceptance. Keep ordinary Windows launch and current default unchanged until an explicit later product promotion decision.
