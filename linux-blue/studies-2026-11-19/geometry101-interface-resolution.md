## Concrete crop distinction

H264 uses coded block dimensions and an intended display rectangle. A coded1088-line frame displayed as1080 is not a user request to crop the picture; rejecting all nonzero codec crop or requiring coded dimensions equal display dimensions would reject normal media. FFmpeg9.0.2 libavcodec/h264_slice.c:init_dimensions (924 onward) explicitly derives display width/height by subtracting SPS crop and stores coded_width/height separately. It also reconciles a bounded container-dimension case. inspection.cjs already requests both coded and display dimensions; media-evidence geometry uses display width/height.

libavcodec/options_table.h:388 defaults apply_cropping to1. libavcodec/decode.c:763–787 validates crop bounds and applies cropping; ffmpeg_dec.c:1597–1598 defers decoder cropping to the CLI, whose video processing at434–440 applies it with AV_FRAME_CROP_UNALIGNED before filters. This is display interpretation, not an explicit application crop filter. FFmpeg CLI documentation also states default all includes codec/container metadata cropping; ffmpeg_demux.c:1457 and1623–1624 implement that choice. Primary public reference: https://ffmpeg.org/doxygen/trunk/structAVCodecContext.html and https://ffmpeg.org/ffmpeg.html . Exact acquired9.0.2 source is the stronger version-specific basis here.

The source and output observations already constrain the relevant dimensions: operation-evidence.cjs checkFrame compares EVERY decoded video width/height/pixel format/color against the observed stream; source-property collection also requires square SAR, left chroma and only the allowlisted SEI side-data type. The actual transform uses contract-resolved dimensions with explicit scale/setsar and no user crop filter; encode-operation output validation checks those transformed dimensions/SAR. A decoder/probe alignment discrepancy does not silently pass those comparisons. Equal dimensions alone are not proof of visual content, so the distinct marker endpoint remains useful, but a new zero-crop acquisition subsystem is not a necessary prerequisite.

Container-level crop side data must remain explicitly outside the first successor: existing streamSideData accepts only identity Display Matrix and source decoded side-data checking is restrictive. Verify that these existing observed relationship/side-data refusals remain intact when successor sourceFacts is split. Do not infer absence of codec crop from zero post-decoder crop fields, and do not conflate container crop metadata with intentional application cropping. Non-square SAR and rotation remain deferred.
